《The Unreasonable Effectiveness of HTML》到底在说什么

Thariq Shihipar 的核心建议不是“把所有文档都改成花哨网页”，而是：当 AI agent 的输出已经从短回复变成长规格说明、代码理解、设计探索和一次性编辑器时，HTML 比 Markdown 更能让人真正读懂、参与并反馈。

核心摘要

这篇文章的关注点是 AI 协作中的输出界面，而不是文件格式洁癖。HTML 被看作让 agent 输出变得可视、可交互、可分享、可回流的载体。

1 个循环

目标是让人更深地处在“读、调、复制回 Claude Code”的循环中。

文章论点

把它压成一句话：Markdown 适合可编辑文本，HTML 适合 AI 生成的复杂认知界面。

信息密度

HTML 能承载更多类型的信息

表格、CSS 设计数据、SVG、图片、交互控件、画布和空间布局都可以放在一个文件里。作者认为这让模型能用更高带宽解释复杂对象。

阅读体验

长输出需要导航和层次

当规格说明和计划超过一百行，线性 Markdown 很容易变成“我知道它有用，但我没读完”。HTML 可以用 tabs、锚点、图示和响应式布局降低阅读阻力。

协作传播

HTML 更像可发链接的工件

Markdown 经常需要平台渲染或附件传递；HTML 上传后就能直接发给同事。文章认为这会显著提高规格、报告和 PR 说明被阅读的概率。

双向互动

读者可以在文档里操作

滑块、开关、拖拽、表单、复制按钮让“看输出”变成“调参数并把结果贴回 agent”。这也是文章最重要的实践转向。

上下文吞吐

Claude Code 的优势是能读很多上下文

作者强调 Claude Code 可以读取文件系统、MCP、浏览器、git 历史等来源，再把这些来源合成为一页可读报告或工具。

参与感

真正的卖点是“更在循环里”

作者担心自己已经不再仔细阅读 agent 的计划；HTML 让他重新愿意审视、比较、操作和反馈。

Markdown 与 HTML 对照

文章不是说 Markdown 没价值，而是说当输出承担“解释、比较、调参、审阅”时，HTML 的表达面更宽。

Markdown 输出

轻、可 diff、适合人手编辑，但线性。

# PR Review ## Summary - Refactors streaming backpressure handling. - Adds retry behavior when the sink is saturated. ## Risk - Backpressure state transitions are hard to scan. - The retry loop may hide timeout errors. ## Suggested checks 1. Verify slow consumer behavior. 2. Add a test for cancellation while paused. 3. Review logs around retry boundaries. ## Diagram source -> buffer -> sink ^ retry | |_______|

HTML artifact

更大、更慢，但能把结构直接呈现出来。

流式链路
发现严重度下一步
取消时仍可能重试高补 cancellation test
日志边界不清晰中标注 retry span
注释落后于实现低同步文档

提示词工作台

作者强调不必一上来做专门 skill，先从“做一个 HTML 文件 / HTML artifact”开始，关键是说清楚这个工件要帮你完成什么。

规划与探索

适合还没有明确方向、需要并排比较方案的任务。

请阅读当前代码和相关上下文，生成一个单文件 HTML artifact。把 4-6 个可行方案并排展示：每个方案包含设计草图、实现路径、风险、适用条件和取舍。最后给出推荐路线、里程碑、关键代码片段和需要我确认的问题。页面要易于快速浏览，并包含目录锚点。

代码审阅

适合复杂 diff、陌生模块、异步流程、性能或安全风险分析。

请创建一个 HTML artifact 来帮我审阅这个 PR。重点解释变更意图、模块调用关系、状态流转和高风险 diff。请渲染关键 diff，添加行内旁注，用严重度颜色标记发现，并给出我应该优先验证的测试清单。不要只总结，请让我能一眼看出代码形状。

设计原型

适合按钮动效、布局方向、流程手感和组件状态比较。

请做一个单文件 HTML 原型，用真实可点击/可调节的控件展示这个交互。加入滑块、分段控制和开关，让我可以调整时长、缓动、密度、状态和颜色。页面需要实时预览，并提供“复制参数”按钮，把当前配置导出成 JSON 或可粘贴回 Claude Code 的 prompt。

一次性编辑器

适合排序、分桶、审核、标注、配置编辑和 prompt 调参。

请根据这份数据创建一个一次性 HTML 编辑器。把项目分组展示，支持拖拽/表单/筛选/校验，标出依赖和冲突。最重要的是页面底部要有导出按钮：复制最终 JSON、复制变更 diff、复制 Markdown 摘要，确保我能把交互结果继续交给 Claude Code 执行。

取舍与边界

最强场景：一次性认知工件

当目标是看懂、比较、调参、审阅或做决策，HTML 值得。因为读者的注意力比 token 更贵。

最大短板：可维护 diff

HTML 很容易产生噪声 diff。如果工件要长期协作维护，仍然需要把数据、样式、脚本和生成流程管住。

风险：漂亮但不可信

视觉层次会放大说服力。对研究报告、代码审阅和事故分析，仍要要求来源、证据、反例和测试路径。

实践建议：HTML 不是默认，是升级档

短备忘、commit message、纯文本协议、需要精准 diff 的规范继续用 Markdown；复杂输出再切 HTML。
